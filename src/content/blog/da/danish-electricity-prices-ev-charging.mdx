**Opdatering, november 2026**

Automationen i afsnittet om opladning kører ikke længere hos mig. Nu bestemmer min elleverandørs smarte opladning, hvornår bilen lader, for to systemer, der styrer det samme, spænder ben for hinanden. Home Assistant bestemmer kun, hvor meget der lades. MySkoda-integrationen er også fjernet, så koden herunder bruger entiteterne fra VW Group Connect. Prisdiagrammet og det billigste vindue bruger jeg stadig hver dag.

</div>

En nat i februar kostede strømmen 0,18 kr./kWh kl. 3 og 3,40 kr./kWh kl. 8. Næsten 20 gange så dyrt på fem timer. Lader bilen efter en fast natplan, er det rent held, hvilken ende af det spænd du rammer.

Home Assistant kan se timepriserne. Resten følger af sig selv.

## Energi Data Service

[Energi Data Service](https://www.energidataservice.dk/) er et gratis offentligt dansk API, og der skal ingen nøgle til. Integrationen i HA henter dagens og morgendagens timepriser for dit prisområde (DK1 eller DK2).

Installer den fra HACS, tilføj den under Integrationer, og vælg dit område. Så får du:

```
sensor.energi_data_service    — aktuel timepris (kr/kWh inkl. moms)
```

Attributterne `raw_today` og `raw_tomorrow` indeholder døgnets priser som `{hour, price}`-objekter, hvor `hour` er et tidspunkt i ISO-format. Morgendagens priser kommer omkring kl. 13, når Nord Pool-auktionen er afgjort.

## Diagrammet

`custom:apexcharts-card` (HACS) med typen `column` passer godt her: hver søjle gælder en hel time, og så skifter prisen. Farvegrænser gør de dyre timer tydelige:

```yaml
type: custom:apexcharts-card
graph_span: 30h
now:
  show: true
  label: Nu
series:
  - entity: sensor.energi_data_service
    type: column
    data_generator: |
      return entity.attributes.raw_today
        .concat(entity.attributes.raw_tomorrow || [])
        .map(h => [new Date(h.hour).getTime(), h.price]);
    color_threshold:
      - value: 0
        color: '#4caf50'
      - value: 1.0
        color: '#ff9800'
      - value: 1.5
        color: '#f44336'
```

Grøn under 1 kr., orange op til 1,50 kr. og rød derover. `concat`-delen tager højde for, at morgendagens priser ikke findes endnu. Uden den fejler diagrammet om formiddagen uden at sige noget.

## Det billigste vindue

### Som template-sensor

En template-sensor, der finder de billigste to sammenhængende timer, der er tilbage i dag:

```yaml
template:
  - triggers:
      - trigger: state
        entity_id: sensor.energi_data_service
      - trigger: time_pattern
        minutes: "/15"
    sensor:
      - name: "Billigste opladningsvindue"
        state: >
          {% set prices = state_attr('sensor.energi_data_service', 'raw_today') %}
          {% if prices %}
            {% set ns = namespace(best_hour=0, best_avg=999) %}
            {% for i in range(prices | length - 1) %}
              {% set avg = (prices[i].price + prices[i+1].price) / 2 %}
              {% if avg < ns.best_avg and as_datetime(prices[i].hour).hour >= now().hour %}
                {% set ns.best_avg = avg %}
                {% set ns.best_hour = as_datetime(prices[i].hour).hour %}
              {% endif %}
            {% endfor %}
            {{ '%02d:00' % ns.best_hour }}
          {% else %}
            ukendt
          {% endif %}
```

Den vises som `02:00` eller `14:00` på dashboardet. Opladningsautomationen brugte den ikke direkte, for den kørte hver time og besluttede ud fra prisen lige nu. Den er stadig nyttig til at tjekke, at bilen lader på et fornuftigt tidspunkt.

De to triggere er der af en grund. En anden af mine template-sensorer løb prislisten igennem på samme måde, og den holdt op med at opdatere uden at skrive så meget som en linje i loggen. Den stod fast på sin første værdi i over to timer, mens priserne skiftede. Uden triggere skal Home Assistant selv finde ud af, hvilke entiteter skabelonen afhænger af, og med en løkke over prislisten gik det galt. Med triggerne bliver sensoren regnet ud igen, hver gang prissensoren ændrer sig, og ellers hvert kvarter.

### Som et dashboard-kort

Vil du helt undgå template-sensoren, kan dette markdown-kort beregne og vise det billigste tidsrum direkte, også for i morgen, når morgendagens priser er kommet:

```yaml
type: markdown
content: >
  {%- set d=state_attr("sensor.energi_data_service","raw_today") -%}
  {%- set r=state_attr("sensor.energi_data_service","raw_tomorrow") -%}
  {%- set tv=state_attr("sensor.energi_data_service","tomorrow_valid") -%}
  {%- set tm=d|map(attribute="price")|min -%}{%- set th=tm*1.25 -%}
  {%- set t=namespace(mi=0,s=0,e=0) -%}
  {%- for h in d -%}{%- if h.price==tm -%}{%- set t.mi=loop.index0 -%}{%- endif -%}{%- endfor -%}
  {%- set t.s=t.mi -%}{%- set t.e=t.mi -%}
  {%- for i in range(23) -%}{%- if t.s>0 and d[t.s-1].price<=th -%}{%- set t.s=t.s-1 -%}{%- endif -%}{%- endfor -%}
  {%- for i in range(23) -%}{%- if t.e<23 and d[t.e+1].price<=th -%}{%- set t.e=t.e+1 -%}{%- endif -%}{%- endfor -%}
  {%- set ts=t.s -%}{%- set te=t.e+1 -%}{%- set tmi=t.mi -%}
  {%- if tv and r -%}
  {%- set rm=r|map(attribute="price")|min -%}{%- set rh=rm*1.25 -%}
  {%- set n=namespace(mi=0,s=0,e=0) -%}
  {%- for h in r -%}{%- if h.price==rm -%}{%- set n.mi=loop.index0 -%}{%- endif -%}{%- endfor -%}
  {%- set n.s=n.mi -%}{%- set n.e=n.mi -%}
  {%- for i in range(23) -%}{%- if n.s>0 and r[n.s-1].price<=rh -%}{%- set n.s=n.s-1 -%}{%- endif -%}{%- endfor -%}
  {%- for i in range(23) -%}{%- if n.e<23 and r[n.e+1].price<=rh -%}{%- set n.e=n.e+1 -%}{%- endif -%}{%- endfor -%}
  {%- set rs=n.s -%}{%- set re=n.e+1 -%}{%- set rmi=n.mi -%}
  {%- endif -%}
  ⚡ **Billigste strøm**

  **I dag** · {{ "%02d:00"|format(ts) }}–{{ "%02d:00"|format(te) }} · lavest **{{ "%.2f"|format(tm)|replace(".",",") }} kr/kWh** kl. {{ "%02d:00"|format(tmi) }}
  {%- if tv and r %}

  **I morgen** · {{ "%02d:00"|format(rs) }}–{{ "%02d:00"|format(re) }} · lavest **{{ "%.2f"|format(rm)|replace(".",",") }} kr/kWh** kl. {{ "%02d:00"|format(rmi) }}
  {%- endif %}

  💡 Start opvaskemaskinen eller vaskemaskinen midt på dagen for at spare mest
```

Logikken: find dagens laveste pris, og udvid tidsrummet med alle tilstødende timer, der ligger højst 25 % over den. Kortet opdaterer sig selv, når sensoren ændrer sig, så der skal ingen separat automation til.

Før kl. 13 findes morgendagens priser ikke, så visningen har to diagramkort, ét over 24 timer og ét over 48, og `binary_sensor.energi_tomorrow_valid` afgør, hvilket der vises. Sensoren slår til omkring kl. 13, når integrationen har hentet morgendagens priser. På billedet er højre halvdel i morgen: 6,63 kr kl. 17, næsten tre gange så meget som de 2,30 kr kl. 4.

Rækken under diagrammet, «Peak grid tariff 17–21 · +0.32 kr/kWh», regnes ud fra attributten `tariffs`, hvor integrationen har min netvirksomheds timetariffer. En skabelon finder de timer, der ligger inden for 10 procent af den højeste tarif, og trækker tariffen for den time, der ligger på medianen fra. I dag giver det kl. 17 til 21 og 0,32 kr/kWh. Mens klokken er mellem 17 og 21, skifter rækkens anden linje til «Peak tariff right now: avoid heavy loads».

Rækkerne «Today» og «Tomorrow» viser laveste og højeste time og gennemsnittet, hentet fra `raw_today`, `raw_tomorrow` og `today_mean`. «Best time today» ser kun på timerne fra nu og frem, så sent på aftenen peger den på kl. 23, som på billedet. Ikonet er grønt, når den billigste time er nu, gult, når den ligger inden for to timer, og ellers blåt.

De to øverste rækker kommer fra Eloverblik, der leverer forbrug et døgn forsinket. Derfor står der 2026-11-07. En automation gemmer døgnets 24 priser kl. 23.55. Når måledata kommer, ganger en anden automation hver times kWh med den times pris og sammenligner med samme forbrug til døgnets gennemsnitspris. Forskellen er tallet «saved»: 8,98 kr for i går og 73 kr for måneden. Det er værdien af at flytte forbrug, ikke en besparelse i forhold til en fast elpris.

Diagrammet til højre er Carnots prognose, som integrationen leverer i attributten `forecast` som timepriser for de kommende dage. Jeg tegner den fra i overmorgen, for de to dage før har rigtige priser. De grønne prikker er hver dags billigste time. På billedet ligger prognosen lavere end de rigtige priser, så jeg bruger den til at se mønsteret: hvilken dag der bliver billig. Den pris, der tæller, kommer kl. 13 dagen før.

## Automationen, der styrede opladningen

Automationen brugte `switch.garage_el_rey_charging` fra [VW Group Connect](https://github.com/its-me-prash/vwgroup-connect-ha) til at starte og stoppe opladningen. Udskift `el_rey` med navnet på din egen bil.

```yaml
alias: Elroq — Smart opladning
trigger:
  - platform: time_pattern
    minutes: "0"
condition:
  - condition: state
    entity_id: binary_sensor.garage_el_rey_charging_cable_connected
    state: "on"
  - condition: numeric_state
    entity_id: sensor.garage_el_rey_battery_level
    below: 90
action:
  - choose:
      - conditions:
          - condition: numeric_state
            entity_id: sensor.energi_data_service
            below: 1.0
        sequence:
          - service: switch.turn_on
            target:
              entity_id: switch.garage_el_rey_charging
      - conditions:
          - condition: numeric_state
            entity_id: sensor.energi_data_service
            above: 1.5
        sequence:
          - service: switch.turn_off
            target:
              entity_id: switch.garage_el_rey_charging
```

Under 1,00 kr.: lad. Over 1,50 kr.: stop. Midt imellem: rør den ikke. Det tomme interval er med vilje. Uden det ville kontakten skifte frem og tilbage hver time, når prisen ligger lige omkring grænsen.

Dengang havde jeg også en `input_boolean`, så jeg kunne tvinge opladningen igennem de morgener, hvor jeg skulle bruge fuldt batteri, uanset prisen.

## Virker det?

Første hele måned: cirka 28 % lavere udgift til opladning end ved opladning hele natten. Besparelsen kommer næsten kun fra de nætter, hvor priserne svinger meget. Der var uger, hvor forskellen var lille, og automationen gjorde ingen forskel.

Det, jeg ikke havde forventet, var, at det ændrede, hvordan jeg tænker på de andre apparater. Elprisdiagrammet er nu et af de kort, jeg kigger mest på, og siden har jeg tilføjet kortet ovenfor, der selv viser det bedste tidspunkt at starte opvaskemaskinen eller vaskemaskinen. Den ændrede vane sparer sandsynligvis mere end den automatiske opladning af bilen.
