Im Februar gab es eine Nacht, in der Strom um 3 Uhr 0,18 DKK/kWh kostete und um 8 Uhr 3,40 DKK/kWh. Fast das 20-Fache innerhalb von fünf Stunden. Wer das Auto nach einem festen Nachtplan lädt, würfelt im Grunde, auf welche Seite dieses Spreads er fällt.

Home Assistant kann die Stundenpreise sehen. Der Rest ergibt sich von selbst.

## Energi Data Service

[Energi Data Service](https://www.energidataservice.dk/) ist eine kostenlose dänische Behörden-API, für die du keinen Schlüssel brauchst. Die HA-Integration holt die heutigen und morgigen Stundenpreise für das eigene Preisgebiet (DK1 oder DK2).

HACS installieren, über Integrationen hinzufügen, Gebiet auswählen. Man bekommt:

```
sensor.energi_data_service    — aktueller Stundenpreis (DKK/kWh inkl. MwSt.)
```

Die Attribute `raw_today` und `raw_tomorrow` enthalten die vollständigen 24-Stunden-Preisarrays als `{hour, price}`-Objekte, wobei `hour` ein ISO-Datetime-String ist. Die Preise für morgen kommen gegen 13 Uhr, wenn die Nord-Pool-Auktion abrechnet.

## Das Diagramm

`custom:apexcharts-card` (HACS) mit Column-Typ ist hier das Richtige: Jede Spalte hält für eine volle Stunde, dann springt sie. Farbschwellenwerte machen die teuren Stunden sofort erkennbar:

```yaml
type: custom:apexcharts-card
graph_span: 30h
now:
  show: true
  label: Jetzt
series:
  - entity: sensor.energi_data_service
    type: column
    data_generator: |
      return entity.attributes.raw_today
        .concat(entity.attributes.raw_tomorrow || [])
        .map(h => [new Date(h.hour).getTime(), h.price]);
    color_threshold:
      - value: 0
        color: '#4caf50'
      - value: 1.0
        color: '#ff9800'
      - value: 1.5
        color: '#f44336'
```

Grün unter 1 DKK, Orange bis 1,50, Rot darüber. Das `concat` behandelt den Fall, dass die morgigen Preise noch nicht verfügbar sind. Ohne dieses `concat` scheitert das Diagramm am Vormittag lautlos.

## Das günstigste Fenster finden

### Als Template-Sensor

Ein Template-Sensor, der den günstigsten zusammenhängenden 2-Stunden-Block findet, der heute noch übrig ist:

```yaml
template:
  - triggers:
      - trigger: state
        entity_id: sensor.energi_data_service
      - trigger: time_pattern
        minutes: "/15"
    sensor:
      - name: "Günstigstes Ladefenster"
        state: >
          {% set prices = state_attr('sensor.energi_data_service', 'raw_today') %}
          {% if prices %}
            {% set ns = namespace(best_hour=0, best_avg=999) %}
            {% for i in range(prices | length - 1) %}
              {% set avg = (prices[i].price + prices[i+1].price) / 2 %}
              {% if avg < ns.best_avg and as_datetime(prices[i].hour).hour >= now().hour %}
                {% set ns.best_avg = avg %}
                {% set ns.best_hour = as_datetime(prices[i].hour).hour %}
              {% endif %}
            {% endfor %}
            {{ '%02d:00' % ns.best_hour }}
          {% else %}
            unbekannt
          {% endif %}
```

Wird als `02:00` oder `14:00` auf dem Dashboard angezeigt. Die Ladeautomatisierung hat ihn nie direkt genutzt, weil sie stündlich lief und nach dem aktuellen Preis entschied. Nützlich ist er trotzdem, um zu prüfen, ob das Auto zu einer vernünftigen Zeit lädt.

Die beiden Trigger haben einen Grund. Ein anderer Template-Sensor von mir ging die Preisliste auf dieselbe Weise durch und hörte auf zu aktualisieren, ohne eine einzige Zeile im Log. Über zwei Stunden blieb er auf seinem ersten Wert stehen, während sich die Preise änderten. Ohne Trigger muss Home Assistant selbst erkennen, von welchen Entitäten ein Template abhängt, und bei einer Schleife über die Preisliste ging das schief. Mit Triggern wird der Sensor bei jeder Änderung des Preissensors neu berechnet und sonst alle 15 Minuten.

### Als Dashboard-Karte

Wer den Template-Sensor ganz vermeiden möchte: Diese Markdown-Karte berechnet das günstigste Fenster direkt und zeigt auch den morgigen Tag, sobald die Preise verfügbar sind:

```yaml
type: markdown
content: >
  {%- set d=state_attr("sensor.energi_data_service","raw_today") -%}
  {%- set r=state_attr("sensor.energi_data_service","raw_tomorrow") -%}
  {%- set tv=state_attr("sensor.energi_data_service","tomorrow_valid") -%}
  {%- set tm=d|map(attribute="price")|min -%}{%- set th=tm*1.25 -%}
  {%- set t=namespace(mi=0,s=0,e=0) -%}
  {%- for h in d -%}{%- if h.price==tm -%}{%- set t.mi=loop.index0 -%}{%- endif -%}{%- endfor -%}
  {%- set t.s=t.mi -%}{%- set t.e=t.mi -%}
  {%- for i in range(23) -%}{%- if t.s>0 and d[t.s-1].price<=th -%}{%- set t.s=t.s-1 -%}{%- endif -%}{%- endfor -%}
  {%- for i in range(23) -%}{%- if t.e<23 and d[t.e+1].price<=th -%}{%- set t.e=t.e+1 -%}{%- endif -%}{%- endfor -%}
  {%- set ts=t.s -%}{%- set te=t.e+1 -%}{%- set tmi=t.mi -%}
  {%- if tv and r -%}
  {%- set rm=r|map(attribute="price")|min -%}{%- set rh=rm*1.25 -%}
  {%- set n=namespace(mi=0,s=0,e=0) -%}
  {%- for h in r -%}{%- if h.price==rm -%}{%- set n.mi=loop.index0 -%}{%- endif -%}{%- endfor -%}
  {%- set n.s=n.mi -%}{%- set n.e=n.mi -%}
  {%- for i in range(23) -%}{%- if n.s>0 and r[n.s-1].price<=rh -%}{%- set n.s=n.s-1 -%}{%- endif -%}{%- endfor -%}
  {%- for i in range(23) -%}{%- if n.e<23 and r[n.e+1].price<=rh -%}{%- set n.e=n.e+1 -%}{%- endif -%}{%- endfor -%}
  {%- set rs=n.s -%}{%- set re=n.e+1 -%}{%- set rmi=n.mi -%}
  {%- endif -%}
  ⚡ **Günstigster Strom**

  **Heute** · {{ "%02d:00"|format(ts) }}–{{ "%02d:00"|format(te) }} · niedrigster **{{ "%.2f"|format(tm)|replace(".",",") }} DKK/kWh** um {{ "%02d:00"|format(tmi) }}
  {%- if tv and r %}

  **Morgen** · {{ "%02d:00"|format(rs) }}–{{ "%02d:00"|format(re) }} · niedrigster **{{ "%.2f"|format(rm)|replace(".",",") }} DKK/kWh** um {{ "%02d:00"|format(rmi) }}
  {%- endif %}

  💡 Spülmaschine oder Waschmaschine mittags starten, um am meisten zu sparen
```

Die Logik: Minimumspreis für den Tag finden, dann das Fenster auf alle benachbarten Stunden innerhalb von 25% dieses Minimums ausweiten. Die Karte wird automatisch aktualisiert, sobald sich der Sensor ändert. Eine separate Automatisierung ist nicht nötig.

## So sieht es auf meinem Tablet aus

![Die Ansicht Energy auf dem Wandtablet: eine Preistreppe für heute und morgen, eine Zeile zum Spitzentarif, Zeilen mit dem Verbrauch von gestern und der Ersparnis des Monats und ein Prognosediagramm von Carnot](/blog-images/energy-prices-tablet-view.webp)

Das ist die Ansicht Energy auf dem Wandtablet. Das Diagramm oben ist die Preistreppe aus dem Abschnitt weiter oben, nur als schlichte orange Linie. Im November liegt der Preis zwischen 2 und 7 kr/kWh, denn der Preis des Sensors enthält den Netztarif schon. Die Schwellen für Grün, Orange und Rot aus dem Beispiel würden deshalb den ganzen Tag Rot zeigen. Ich habe die Farben weggelassen.

Das Diagramm zeigt heute und morgen. Vor 13 Uhr gibt es für morgen noch keine Preise, deshalb hat die Ansicht zwei Diagrammkarten, eine über 24 und eine über 48 Stunden, und `binary_sensor.energi_tomorrow_valid` entscheidet, welche zu sehen ist. Der Sensor springt gegen 13 Uhr an, sobald die Integration die Preise für morgen geholt hat. Auf dem Bild ist die rechte Hälfte morgen: 6,63 kr um 17 Uhr, fast das Dreifache der 2,30 kr um 4 Uhr.

Die Zeile unter dem Diagramm, „Peak grid tariff 17–21 · +0.32 kr/kWh“, wird aus dem Attribut `tariffs` berechnet, in dem die Integration die Stundentarife meines Netzbetreibers hält. Ein Template nimmt die Stunden, die höchstens 10 Prozent unter dem höchsten Tarif liegen, und zieht den Tarif der Medianstunde ab. Heute ergibt das 17 bis 21 Uhr und 0,32 kr/kWh. Liegt die Uhrzeit in diesem Fenster, wechselt die zweite Zeile zu „Peak tariff right now: avoid heavy loads“.

Die Zeilen „Today“ und „Tomorrow“ zeigen die billigste und die teuerste Stunde und den Durchschnitt, gelesen aus `raw_today`, `raw_tomorrow` und `today_mean`. „Best time today“ schaut nur auf die Stunden ab jetzt. Spät am Abend zeigt sie deshalb auf 23 Uhr, wie im Bild. Das Symbol ist grün, wenn die billigste Stunde jetzt ist, gelb, wenn sie in höchstens zwei Stunden kommt, sonst blau.

Die beiden obersten Zeilen kommen von Eloverblik, das den Verbrauch einen Tag später liefert. Darum steht im Bild 2026-11-07. Eine Automatisierung speichert um 23:55 die 24 Preise des Tages. Wenn die Zählerdaten da sind, multipliziert eine zweite Automatisierung die kWh jeder Stunde mit dem Preis dieser Stunde und vergleicht das mit demselben Verbrauch zum Tagesdurchschnittspreis. Der Unterschied ist der Wert „saved“: 8,98 kr für gestern, 73 kr für den Monat. Das ist der Wert der Lastverschiebung, keine Ersparnis gegenüber einem Festpreis.

Rechts steht die Prognose von Carnot, die die Integration im Attribut `forecast` als Stundenpreise für die nächsten Tage liefert. Ich zeichne sie ab übermorgen, weil für die zwei Tage davor echte Preise vorliegen. Die grünen Punkte markieren die billigste Stunde jedes Tages. Im Bild liegt die Prognose niedriger als die echten Preise, deshalb lese ich sie nur als Muster: Welcher Tag wird billig? Der Preis, der zählt, kommt um 13 Uhr am Vortag.

## Die Ladeautomatisierung

Die Automatisierung nutzte `switch.garage_el_rey_charging` aus [VW Group Connect](https://github.com/its-me-prash/vwgroup-connect-ha), um das Laden zu starten und zu stoppen. Ersetze `el_rey` durch den Namen deines Autos.

```yaml
alias: Elroq — Smart laden
trigger:
  - platform: time_pattern
    minutes: "0"
condition:
  - condition: state
    entity_id: binary_sensor.garage_el_rey_charging_cable_connected
    state: "on"
  - condition: numeric_state
    entity_id: sensor.garage_el_rey_battery_level
    below: 90
action:
  - choose:
      - conditions:
          - condition: numeric_state
            entity_id: sensor.energi_data_service
            below: 1.0
        sequence:
          - service: switch.turn_on
            target:
              entity_id: switch.garage_el_rey_charging
      - conditions:
          - condition: numeric_state
            entity_id: sensor.energi_data_service
            above: 1.5
        sequence:
          - service: switch.turn_off
            target:
              entity_id: switch.garage_el_rey_charging
```

Unter 1,00 DKK: laden. Über 1,50 DKK: stoppen. Dazwischen: nichts ändern. Die Totzone ist Absicht. Ohne sie würde der Schalter jede Stunde hin und her schalten, wenn die Preise um den Schwellenwert schweben.

Dazu gab es damals einen `input_boolean`, mit dem ich an Morgen, an denen ich unabhängig vom Preis einen vollen Akku brauchte, das Laden erzwingen konnte.

## Spart es wirklich?

Erster vollständiger Monat: ca. 28% niedrigere Ladekosten im Vergleich zu dauerhaftem Nachtladen. Die Einsparungen kamen fast ausschließlich aus den Nächten mit großen Preisspreads. In manchen Wochen war der Spread gering, und die Automatisierung machte keinen Unterschied.

Was ich nicht erwartet hatte: Es veränderte, wie ich über andere Geräte nachdenke. Das Strompreisdiagramm ist jetzt eine der meistgeprüften Karten auf meinem Dashboard, und ich habe seitdem die Fenster-Karte oben hinzugefügt, die automatisch die beste Zeit zum Betrieb von Spülmaschine oder Waschmaschine anzeigt. Diese Verhaltensänderung spart wahrscheinlich mehr als das automatisierte Laden selbst.
