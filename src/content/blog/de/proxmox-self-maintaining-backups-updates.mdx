Mein Home Assistant läuft als VM auf einem einzelnen Proxmox-Server, und lange Zeit kümmerte sich der Server um nichts. Die Backups lagen auf derselben SSD wie das System, Updates warteten, bis ich daran dachte, und wenn ein Job fehlschlug, erfuhr ich nichts davon. Hier steht, was ich an einem Abend geändert habe, was dabei schiefging und was ich noch nicht getestet habe.

## Ausgangslage

Proxmox VE 9.2 mit einem Gast, Home Assistant OS, auf einer einzelnen SATA-SSD mit 256 GB. Die Platte hat rund 56.000 Betriebsstunden. SMART meldet weiterhin PASSED, aber bei einer so alten Platte kommt zuerst eine Kopie außerhalb des Geräts, und der Server hatte überhaupt keinen Backup-Job.

## Ein wöchentliches Backup, das das Gerät verlässt

Das Backup selbst ist ein normaler Proxmox-Job: sonntags um 03:00 Uhr, Snapshot-Modus, zstd, die letzten zwei bleiben erhalten. Die Home-Assistant-VM kommt auf etwa 4 GB, und der Job dauert rund eine Minute.

Zum richtigen Backup wird es erst durch die Kopie auf Google Drive. Ich nutze rclone mit dem Scope `drive.file`, damit das Token auf dem Hypervisor nur Dateien sieht, die rclone selbst angelegt hat, und nicht den Rest meines Drives. Der Server hat keinen Browser, also läuft die Autorisierung einmal auf meinem PC:

```bash
# auf einem PC mit Browser
rclone authorize "drive" --drive-scope drive.file

# auf dem Proxmox-Server, mit dem ausgegebenen Token
rclone config create gdrive drive scope=drive.file config_is_local=false token='{"access_token":"..."}'
```

Danach wird der PC nicht mehr gebraucht. Ein Cron-Job um 05:00 Uhr kopiert die Backups der Home-Assistant-VM nach Drive, aber nur, wenn das neueste lokale Backup frisch ist und `zstd -t` besteht:

```bash
rclone copy /mnt/ext/dump gdrive:Proxmox-Backups --include 'vzdump-qemu-100-*'
```

Meine erste Version nutzte `rclone sync`, das Drive zu einem exakten Spiegel macht. Für ein Backup ist das das falsche Werkzeug: Ein leerer oder gelöschter lokaler Ordner hätte am nächsten Sonntag alle Kopien auf Drive gelöscht. Das Skript nutzt jetzt `rclone copy`, bricht ab, wenn das neueste lokale Backup fehlt, älter als acht Tage ist oder `zstd -t` nicht besteht, vergleicht die MD5-Summe auf Drive mit der lokalen Datei und löscht erst danach die ältesten Kopien dort, sodass die vier neuesten bleiben. Ein zweiter kleiner Job packt die Serverkonfiguration in ein Archiv mit 23 KB: `/etc/pve` ohne den Ordner `priv` und ohne `*.key`-Dateien, die Netzwerkdatei und meine eigenen Skripte. Geheimnisse bleiben absichtlich draußen. Ein neuer Server braucht deshalb ein neues ACME-Token und eine neue Google-Autorisierung.

Meine erste Cron-Zeile zeigte auf `/mnt/pve/ext/dump`, einen Pfad, den es nicht gibt. Der richtige ist `/mnt/ext/dump`. Ein Lauf mit `rclone --dry-run` zeigte das vor dem ersten Sonntag, und deshalb lasse ich neue rclone-Zeilen jetzt immer zuerst mit `--dry-run` laufen.

## Alarme, die das Handy erreichen

Proxmox schickt seine Benachrichtigungen an `root`, und auf meinem Server landeten sie nirgends. Es gibt kein Mail-Relay, und zwei Nachrichten hingen in der Warteschlange. Statt Mail einzurichten, habe ich genutzt, was ohnehin nebenan läuft: Ein Benachrichtigungsziel vom Typ Webhook in Proxmox ruft eine Webhook-Automation in Home Assistant auf, die eine Push-Nachricht ans Handy schickt.

```yaml
triggers:
  - trigger: webhook
    webhook_id: pve-<zufällige-id>
    allowed_methods: [POST]
    local_only: true
actions:
  - action: notify.mobile_app_<handy>
    data:
      title: "Proxmox: {{ trigger.json.title }}"
      message: "{{ trigger.json.message }}"
```

Proxmox verlangt, dass der Body und jeder Header-Wert base64-kodiert sind. Mein erster Test scheiterte mit `could not decode UTF8 string from base64, key 'Content-Type'`. Eine Regel für die Schweregrade warning, error und unknown schickt nur, was Aufmerksamkeit braucht, und das Handy bleibt sonst still.

## Let's Encrypt, ohne einen Port zu öffnen

Das lokale DNS von UniFi kann einen Namen auf eine Adresse zeigen lassen, aber nicht auf einen Port, deshalb bräuchte `proxmox.szimnau.dk` weiterhin `:8006`. Ein kleiner systemd-Dienst leitet daher Port 443 auf dem Server auf 8006 um. Ich habe die Regel auf die eigene Adresse des Servers beschränkt, weil eine pauschale Umleitung von 443 auch HTTPS-Verkehr der Gäste erfassen könnte, der über die Bridge läuft:

```bash
iptables -t nat -A PREROUTING -d <server-ip> -p tcp --dport 443 -j REDIRECT --to-ports 8006
```

Für das Zertifikat habe ich den eingebauten ACME-Client von Proxmox mit dem Cloudflare-DNS-Plugin genutzt. Die DNS-Validierung braucht keinen eingehenden Zugriff, es wird also nichts nach außen geöffnet. Das Plugin war schon eingerichtet, aber das Zertifikat hatte nie jemand bestellt, und deshalb warnte der Browser weiter. Nach einer Bestellung war es für beide Namen gültig und erneuert sich selbst. Proxmox speichert das Cloudflare-Token im Klartext und gibt es über die API heraus, deshalb sollte es nur das Recht haben, DNS in einer einzigen Zone zu bearbeiten.

## Automatische Updates mit Bremsen

Das Update-Skript läuft sonntags um 06:00 Uhr, nach Backup und Upload. Es tut nichts, wenn nicht alle diese Prüfungen bestanden sind:

- Es gibt ein Backup der Home-Assistant-VM, das jünger als 12 Stunden ist und dessen Upload auf Drive bestätigt wurde.
- Das Update würde keine Pakete entfernen.
- Es ist keine neue Hauptversion von Proxmox erschienen. Kleinere Schritte wie 9.2 auf 9.3 laufen durch und stehen in der Nachricht, ein Sprung auf Version 10 schickt mir stattdessen eine Nachricht.
- Neu gestartet wird nur, wenn ein installierter Kernel neuer ist als der laufende, und nicht, während ein Backup läuft.

Vor dem Neustart wartet das Skript zehn Minuten und sagt dem Handy Bescheid. Ein systemd-Dienst schickt außerdem nach jedem Start eine Nachricht, sobald die VM läuft, Home Assistant antwortet und zwei weitere Minuten vergangen sind. Kommt diese Nachricht nicht innerhalb von etwa zwölf Minuten, ist Home Assistant nicht zurückgekommen. Wenn kein Neustart ansteht, räumt das Skript außerdem alte Kernel auf und behält den laufenden und die zwei neuesten.

```bash
OLDK=$(uname -r)
NEWK=$(ls /boot/vmlinuz-* | sed 's|/boot/vmlinuz-||' | sort -V | tail -n 1)
[ "$NEWK" != "$OLDK" ] && shutdown -r +10
```

Die erste Version des Skripts brach ab, sobald es keine Pakete zu installieren gab. Das hätte den Neustart für einen schon installierten Kernel übersprungen, und genau so war der Zustand meines Servers. Der Probelauf (`-n`) hat es vor dem echten Lauf aufgedeckt.

## Was ich getestet habe und was nicht

Der unbeaufsichtigte Sonntagslauf hat funktioniert. Um 03:00 Uhr machte Proxmox das Backup, um 04:00 Uhr wurde die Serverkonfiguration gepackt, um 05:00 Uhr lagen beide auf Drive (3,6 GB und 18 KB), und um 06:00 Uhr lief das Update-Skript, fand nichts zu installieren, sah, dass der laufende Kernel schon der neueste war, und ließ den Server in Ruhe. Am Abend davor hatte ein echter Lauf zwar nichts installiert, aber den Neustart für den wartenden Kernel eingeplant, und Home Assistant antwortete etwa eine Minute nach der Rückkehr von Proxmox wieder.

Eine Prüfung ist fehlgeschlagen. Die Nachricht „Proxmox is up“ nach diesem Neustart kam nie auf meinem Handy an. Meine beste Erklärung: Home Assistant antwortet auf Port 8123, bevor seine Webhooks bereit sind, die Nachricht lief also ins Leere. Das Skript wartet jetzt zwei Minuten, nachdem Home Assistant antwortet, bevor es sendet. Ob die Korrektur wirkt, habe ich noch nicht durch einen weiteren Neustart geprüft.

Die Wiederherstellung funktioniert. Ich habe das Backup der letzten Nacht von Drive geladen, geprüft, dass es Byte für Byte mit der lokalen Datei übereinstimmt (gleiche Größe und gleiche MD5-Summe), und es mit `qmrestore --unique 1` in eine temporäre VM zurückgespielt. Das dauerte etwa zwei Minuten. Die VM habe ich nie gestartet, weil eine zweite Home-Assistant-Instanz im selben Netz und mit demselben Zigbee-Stick Ärger machen würde. Stattdessen habe ich die Datenpartition über ein Loop-Gerät schreibgeschützt eingehängt und darin die Home-Assistant-Konfiguration, die Automationen und die Datenbank gefunden, und danach die VM wieder gelöscht. Proxmox bringt `kpartx` nicht mit, deshalb habe ich die Partitionen mit `losetup -rP` sichtbar gemacht.

Das belegt die Dateien und den Aufbau der Platte, nicht aber, dass die wiederhergestellte VM startet.

Der Wiederherstellungstest läuft jetzt jedes Quartal von selbst. Er lädt das neueste Backup von Drive, vergleicht die MD5-Summe mit der, die Drive meldet, stellt es in einer temporären VM wieder her, lässt SQLite eine Kopie der Home-Assistant-Datenbank prüfen, löscht alles wieder und schickt das Ergebnis aufs Handy. Ein Lauf des fertigen Skripts dauerte gut vier Minuten und las 762.224 Zeilen Verlauf ohne Fehler.

Auch der Fehlerweg funktioniert. Ich habe das Upload-Skript auf einen leeren Ordner gerichtet. Es hat angehalten, bevor es Drive berührte, und der Alarm ging über Home Assistant raus. Eine Durchsicht meiner Skripte fand das oben beschriebene `sync`-Problem und einen alten wöchentlichen Job in Roots Crontab, der ein Skript von GitHub holte und als root ausführte. Den habe ich entfernt. Die Notfallanleitung liegt jetzt im selben Drive-Ordner wie die Backups, und Home Assistant macht jede Nacht selbst ein Backup auf Drive als zweite Schicht.
