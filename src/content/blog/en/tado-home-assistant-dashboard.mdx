**Update, November 2026:** I have one Tado zone now, not five: the Daikin heat pump in the living room. The grid of five zones, the loops over five climate entities and the presence and window automations further down describe an earlier layout. The breathing animation works the same on a single card, so I left that code as it was.

The card I use today is a Mushroom climate card named "Living room" with plus and minus buttons and mode buttons for off, auto, cool, heat, dry and fan only. Its icon glows orange and breathes while the pump is heating, glows blue while cooling, green when only the fan runs, and turns grey when idle. The whole card dims to 40% opacity while the zone is off or idle.

I don't run the away setback or the open-window alert today. The windows are watched by IKEA sensors instead, which I wrote about in [the window Blueprint post](/en/blog/window-heating-automation/). I also use the Tado Hijack integration from HACS now instead of the built-in one, because it manages Tado's daily API quota.

Tado's HA integration is one of the best out of the box. It's built into HA, no HACS needed. You need the Tado Internet Bridge hardware and a Tado account. Add the integration, sign in, and all your zones appear as `climate.*` entities with full support. State updates come back in under five seconds. It just works.

So the heating part was easy. The interesting part was making the dashboard tell you something at a glance.

## The breathing animation

The problem with displaying 5 climate cards in a grid: they all look identical whether the heating is running or not. Temperature displayed, setpoint displayed, mode displayed. But you can't tell which zones are actively firing the boiler.

I added a CSS keyframe animation via `card_mod` that applies only when the `hvac_action` attribute is `heating`:

```yaml
type: custom:mushroom-climate-card
entity: climate.zone_living_room
card_mod:
  style: |
    :host {
      {% if state_attr('climate.zone_living_room', 'hvac_action') == 'heating' %}
      animation: breathe 3s ease-in-out infinite;
      {% endif %}
    }
    @keyframes breathe {
      0%, 100% { filter: drop-shadow(0 0 4px rgba(255, 100, 0, 0.3)); }
      50%       { filter: drop-shadow(0 0 14px rgba(255, 100, 0, 0.75)); }
    }
```

Active zones pulse with a warm orange glow. Idle zones are static. Across a 5-zone grid it's immediately obvious which rooms are actually consuming energy, something no static dashboard had given me before.

A visitor asked if the house was breathing. That felt right.

Duplicate the block for each zone and swap the entity ID. The Jinja2 inside `card_mod` evaluates at render time, so each card independently decides whether to animate.

## The two living room cards today

![The Living room climate card showing Auto and 20.5 °C with a setpoint of 22, above the Price-shifted preheating card with a preheat window at 04:00 and an afternoon top-up at 12:00](/blog-images/tado-living-room-card.webp)

The top card is the one from the update note: a single Mushroom climate card for the Daikin. It shows the mode and the room temperature ("Auto · 20.5 °C") and the setpoint with plus and minus. The orange pulse from the section above sits on its icon and only appears while the heat pump is heating. A screenshot can't show that, so the card stands still here.

The card below is the part I like. The Daikin follows Tado's own schedule, which lives in Tado's cloud and heats at fixed times. The electricity price changes by the hour, so a fixed time is rarely the cheapest one. Every evening at 20:35 an automation reads tomorrow's prices from `sensor.energi_data_service`, finds the cheapest two-hour block between 02:00 and 06:00 and the cheapest three-hour block between 12:00 and 18:00, and stores the start times in two time helpers. "Preheat window" and "Afternoon top-up" show them: 04:00 and 12:00 in the screenshot.

When a start time arrives, a second automation asks Tado for heat: 30 °C for the preheat, 23 °C for the top-up. It uses an overlay that lasts until the next block, so Tado takes over again by itself when the next block of its own schedule starts (normally 05:45 in the morning and 17:00 in the afternoon). I never end up with a manual override I forgot about. This morning it went to heat at 04:00 and was back on Tado's schedule at 05:45.

There is a guard. If the living room is already at 20 °C or more, the automation does nothing, because there is no point paying for heat in a warm room. The afternoon top-up skipped itself at 12:00 yesterday and today for that reason.

It took me until late October to get this working. Tado rejected the command because the heat pump's fan settings were missing, so the fixed schedule did all the work. Now the automation refreshes the pump's capabilities first when they are missing.

## Layout

Five cards in a 2-column grid via `custom:layout-card` (HACS), wrapped in a glass `custom:stack-in-card` (HACS), with `card_mod` (HACS) for the CSS animations:

```yaml
type: custom:stack-in-card
card_mod:
  style: |
    ha-card {
      background: rgba(255,255,255,0.05) !important;
      backdrop-filter: blur(15px) !important;
      border: 1px solid rgba(255,255,255,0.10) !important;
      box-shadow: 0 8px 32px rgba(0,0,0,0.3) !important;
      border-radius: 28px !important;
    }
    ha-card::before { display: none !important; }
cards:
  - type: custom:layout-card
    layout_type: custom:grid-layout
    layout:
      grid-template-columns: 1fr 1fr
      grid-gap: 8px
      padding: 8px
    cards:
      - type: custom:mushroom-climate-card
        entity: climate.zone_living_room
        show_temperature_control: true
        card_mod:
          style: |
            :host {
              {% if state_attr('climate.zone_living_room', 'hvac_action') == 'heating' %}
              animation: breathe 3s ease-in-out infinite;
              {% endif %}
            }
            @keyframes breathe {
              0%, 100% { filter: drop-shadow(0 0 4px rgba(255,100,0,0.3)); }
              50%       { filter: drop-shadow(0 0 14px rgba(255,100,0,0.75)); }
            }
      # repeat for each zone
```

`show_temperature_control: true` adds +/- buttons directly on the card. Small thing, but it means adjusting a zone doesn't require navigating anywhere.

## Presence-based setback

When everyone leaves, drop everything to 17°C. When someone returns, restore auto mode (Tado's own schedule takes over):

```yaml
alias: Tado — Away setback
trigger:
  - platform: state
    entity_id: group.household_members
    to: not_home
action:
  - repeat:
      for_each:
        - climate.zone_living_room
        - climate.zone_office
        - climate.zone_bedroom
        - climate.zone_bathroom
        - climate.zone_hallway
      sequence:
        - service: climate.set_temperature
          target:
            entity_id: "{{ repeat.item }}"
          data:
            temperature: 17

alias: Tado — Restore on return
trigger:
  - platform: state
    entity_id: group.household_members
    to: home
action:
  - repeat:
      for_each: [climate.zone_living_room, climate.zone_office, climate.zone_bedroom,
                 climate.zone_bathroom, climate.zone_hallway]
      sequence:
        - service: climate.set_hvac_mode
          target:
            entity_id: "{{ repeat.item }}"
          data:
            hvac_mode: auto
```

I use this instead of Tado's built-in geofencing because my presence detection combines phone GPS, UniFi device tracking, and a `person.*` entity. It's more reliable than Tado's app alone, which occasionally decides I've left when I'm just in the back garden.

## Window detection

Tado's open window detection is hardware-based: the TRV measures a sudden temperature drop and pauses heating automatically. HA exposes this as `binary_sensor.zone_*_window`.

I added a notification for windows left open more than 20 minutes during active heating. The bathroom window is the usual culprit. The automation has probably saved more in heating costs than anything else I've built around Tado.

```yaml
alias: Tado — Open window alert
trigger:
  - platform: state
    entity_id:
      - binary_sensor.zone_living_room_window
      - binary_sensor.zone_bathroom_window
    to: "on"
    for:
      minutes: 20
condition:
  - condition: template
    value_template: >
      {{ state_attr(trigger.entity_id | replace('binary_sensor.', 'climate.') | replace('_window', ''), 'hvac_action') == 'heating' }}
action:
  - service: notify.all_devices
    data:
      title: "Window open — heating running"
      message: >
        {{ trigger.entity_id
           | replace('binary_sensor.zone_','')
           | replace('_window','')
           | replace('_',' ')
           | title }} has been open for 20 minutes.
```
